\section{Introduction}

The robot must autonomously explore a simulated park environment while performing a series of perception, navigation, and interaction tasks to complete the mission. The environment is visually rich, contains humans, bridges, birds, and colored rings, and requires semantic understanding and spatial awareness.

\begin{itemize}

    \item \textbf{Autonomous Exploration and Mapping:}
    \begin{itemize}
        \item Explore the park using SLAM to construct a map.
        \item Autonomously navigate around the park using the constructed map.
        \item Avoid restricted regions such as water and grass.
        \item Divide the park into three sectors: East, Center, and West for systematic coverage.
    \end{itemize}

    \item \textbf{Bridge Navigation:}
    \begin{itemize}
        \item Detect and traverse narrow bridge structures using visual cues from the arm-mounted camera.
        \item Identify the end of the bridge via ground appearance changes and plan a smooth transition onto the island.
        \item Search for a final red X marker on the island indicating a stopping point.
    \end{itemize}

    \item \textbf{Ring Detection and Navigation:}
    \begin{itemize}
        \item Detect colored rings in the environment using RGB-D input and fit ellipses to segment the inner and outer boundaries.
        \item Use rings as navigation waypoints to localize the areas where birds are likely to be found.
        \item Classify ring colors (red, green, blue, black) based on HSV hue histograms and cosine similarity.
    \end{itemize}

    \item \textbf{Bird Detection and Classification:}
    \begin{itemize}
        \item Detect all 24 flat bird images placed on the ground, usually near the rings.
        \item Recognize the species of each bird using machine learning classification.
        \item Move close to each detected bird, orient the camera, and take a photograph.
        \item Log the bird’s image and species name for verification and reporting.
        \item Generate a final PDF report listing all detected and classified birds.
    \end{itemize}

    \item \textbf{Human Detection and Interaction:}
    \begin{itemize}
        \item Detect and approach humans in the park using face detection.
        \item Identify each person’s gender.
        \item Engage in a dialogue to determine their favorite bird species:
        \begin{itemize}
            \item Women state their favorite bird directly.
            \item Men require the robot to ask multiple times; the bird repeated twice or confirmed with “yes” is accepted as the favorite.
        \end{itemize}
        \item Use previously gathered map and bird data to make conversation context-aware.
    \end{itemize}

    \item \textbf{Task Completion:}
    \begin{itemize}
        \item The robot must visit all regions (East, Center, West).
        \item Complete the bird and human interaction objectives.
        \item Use ground segmentation and visual navigation to reach the final goal marked with a red X.
    \end{itemize}

\end{itemize}




Our team, "Pi," focused on developing modular solutions for each sub-problem and integrating them into a cohesive system using the Robot Operating System (ROS). This report outlines the methods employed, the implementation details, the performance of our system, the division of work among team members, and concludes with a discussion of the challenges faced and lessons learned.

\section{Methods}
This section describes the core methods used in our system.






\subsection{Adaptive Monte Carlo Localization (AMCL)}
AMCL is a probabilistic localization algorithm that uses a particle filter to track the pose of a robot against a known map \cite{fox2003monte}. It updates particle weights based on laser scan matching and odometry motion models. In our simulation, AMCL was used for global localization of the TurtleBot 4 within a pre-built occupancy grid map during inspection tasks.

\subsection{Simultaneous Localization and Mapping (SLAM)}
SLAM algorithms enable a robot to build a map of an unknown environment while simultaneously determining its location within that map \cite{durrant}. In our simulation, SLAM (via \texttt{slam\_toolbox}) was used to generate the initial map of the environment before running AMCL-based inspection runs.

\subsection{Harris Corner Detection}
Harris corner detection is a classical method for identifying interest points (corners) in an image by analyzing changes in intensity gradients \cite{harris1988combined}. In our simulation, it was used in the \texttt{detect\_rings.py} node to extract robust features of ring-like structures in RGB images.

\subsection{Canny Edge Detection}
Canny edge detection is a multi-stage algorithm that detects edges by applying Gaussian smoothing, gradient calculation, non-maximum suppression, and hysteresis thresholding \cite{canny}. In our simulation, it was used as part of the pre-processing pipeline in both \texttt{detect\_rings.py} and \texttt{video\_to\_audio.py} for detecting edges of rings and structural video features, respectively.

\subsection{Visual Transformer (ViT)}
Visual Transformers \cite{vistra} adapt Transformer architectures to image processing by representing images as sequences of patches. In our simulation, ViT-based models were used in the bird classification pipeline (\texttt{bird\_classifier.py}) to classify bird species detected by YOLO-based object detectors.

\subsection{Coordinate Transforms in ROS 2}
Coordinate transforms are essential for expressing sensor data and robot poses in consistent frames of reference \cite{foote2013tf}. In our simulation, the \texttt{tf2} library was used extensively in \texttt{detect\_people.py} and \texttt{detect\_rings.py} to transform 3D positions from camera frames to the global \texttt{map} frame for navigation and inspection.

\subsection{Random Sample Consensus (RANSAC)}
RANSAC is a robust model fitting algorithm that iteratively selects random data subsets to estimate model parameters and identify inliers \cite{fischler1981random}. In our simulation, RANSAC was employed to fit planes to point clouds around detected faces and rings, allowing estimation of surface normals for viewpoint planning.

\subsection{Hough Transform}
The Hough transform is a feature extraction technique used to detect parameterized shapes (e.g., lines, circles) in images \cite{duda1972use}. In our simulation, the Hough Circle Transform was used in early versions of \texttt{detect\_rings.py} for detecting circular ring candidates in pre-processed edge maps.

\subsection{Otsu's Thresholding}
Otsu's method automatically determines an optimal global threshold to separate foreground and background by maximizing inter-class variance \cite{otsu1979threshold}. In our simulation, Otsu's thresholding was applied to pre-processed grayscale images in \texttt{detect\_rings.py} to enhance ring visibility before edge and feature extraction.

\subsection{YOLO}
\cite{Redmon2016}, obtained from \href{https://github.com/ultralytics/ultralytics}{Ultralytics}. We use a general YOLOv8n model to perform fast detection of "bird" candidates in the robot's camera feed and face detection.

\subsection{ResNet18}
\cite{resnet} ResNet-18 (Residual Network) was used in classification system for birds. It is a deep convolutional neural network that leverages residual connections to enable effective training of relatively deep models, mitigating the vanishing gradient problem and facilitating the learning of complex visual features.

\section{Implementation and Integration}
This section details how the aforementioned methods were implemented and integrated into a distributed robotic system using ROS.

\subsection{Autonomous Navigation}
Our navigation system integrates SLAM-based mapping, dynamic path planning, and robust localization using standard ROS 2 tools.
\begin{itemize}
    \item \textbf{Mapping:} Utilizing SLAM (Simultaneous Localization and Mapping) techniques, such as GMapping, to build a 2D occupancy grid map of the simulated environment as we drive the robot.
    \item \textbf{Path Planning:} Our robot performs path planning using the ROS 2 Navigation Stack (Nav2), which is responsible for computing safe and efficient paths to target locations. Path planning is initiated when \texttt{RobotCommander} node sends a goal to the \texttt{NavigateToPose} action server, provided by the \texttt{nav2\_bt\_navigator} node. Internally, \texttt{nav2\_bt\_navigator} runs a Behavior Tree that coordinates the overall navigation process. It uses the \texttt{nav2\_planner} node, which performs global path planning using graph-based search algorithms such as A* or Dijkstra's algorithm on a 2D occupancy grid. Once a global path is found, the \texttt{nav2\_controller} node handles local path following and dynamic obstacle avoidance using a local planner. In our architecture, \texttt{RobotCommander} acts as a high-level client, while the actual path planning, map updates, and path execution are handled by Nav2 nodes and core ROS 2 action mechanisms. 
    \item \textbf{Exploration Strategy:} To ensure comprehensive coverage of the environment, we compute navigation waypoints from the acquired map. This is done by fitting lines using Hough transform and slicing the fitted lines into segments of 0.2 meters. For each segment a navigation waypoint is set as a point 0.7 meters from the middle of the line segment to each side of the line. If the location is illegal based on the map, it is removed. If the generated waypoint is too close to any adjacent wall for safe navigation of the robot, it is moved away perpendicular to that wall, ensuring 0.5 meter clearance of each waypoint. Each navigation waypoint also has a direction which points towards the wall. The robot navigator then visits these goals in greedy way, selecting the closest goal based on A* distance.
    \item \textbf{Localization:} Continuous localization using AMCL (Adaptive Monte Carlo Localization) was used in all parts of the task to track the robot's pose within the map accurately.
\end{itemize}

The `planner.py` and `navigator.py` scripts encapsulate these functionalities.

\subsection{Finetuning ResNet-18 for Bird Species Classification}

We fine-tune ResNet-18 on CUB\_200\_2011 dataset originally containing 200 classes of birds. For our task we used a subset of 24 classes \ref{appendix:birds}. Input images were resized to 224x224 pixels, augmented using random horizontal flips and color jitter, and normalized before being passed to the network. The model is trained using the Adam optimizer with a learning rate of $10^{-4}$, and the cross-entropy loss:
\[
\mathcal{L}_{\text{class}} = - \sum_{i=1}^{N} y_i \log(\hat{y}_i)
\]

\subsection{Ring Detection}

Ring detection is performed using a series of synchronized image processing and 3D analysis steps implemented in the \texttt{ring\_detector.py} node. The pipeline is triggered only when the robot reaches specific states such as \texttt{ARRIVED\_AT\_GOAL} or \texttt{MOVING\_CLOSER\_TO\_BIRD}. The key steps are:

\begin{itemize}
    \item \textbf{Input Synchronization:} The detector subscribes to synchronized RGB images, depth images, and point clouds from the top arm-mounted camera.

    \item \textbf{Preprocessing:} The RGB image is converted to HSV color space, and the depth image is normalized and clamped to 2.0 meters to focus detection on nearby rings. This constraint improves reliability by ignoring distant, noisy shapes.

    \item \textbf{Edge and Corner Filtering:}
    \begin{itemize}
        \item \textbf{Edge Detection:} The depth image is passed through a Canny edge detector with thresholds of 50 and 150.
        \item \textbf{Corner Detection:} Harris corner detection (block size 5, kernel size 3, k=0.1) is applied to the Canny edge map to identify and remove edge regions that belong to corners. This helps separate overlapping objects, such as birds close to rings and the rods holding the rings in place.
        \item \textbf{Edge Spur Removal:} Small spurs (up to 25 pixels long) are pruned by tracing from edge endpoints, reducing leftover artifacts by imprecise harris corner removal.
    \end{itemize}

    \item \textbf{Contour and Ellipse Detection:}
    \begin{itemize}
        \item Contours are extracted from the cleaned edge image.
        \item Contours shorter than 10 points or too linear (with $>$85\% of points lying close to a line) are discarded.
        \item Remaining contours are fitted with ellipses (only if they have $\geq$9 points).
    \end{itemize}

   \item \textbf{Ring Candidate Filtering:}
    \begin{itemize}
        \item To identify actual ring shapes, the algorithm considers all pairs of fitted ellipses and tests whether one could be the inner and the other the outer boundary of the same ring.
        \item Each pair is evaluated using several geometric constraints to filter out false positives:
        \begin{itemize}
            \item The distance between the centers of the two ellipses must be $\leq$ 1.0 pixel to ensure they are concentric.
            \item The difference in orientation angles between the ellipses must be $\leq$ 40° to enforce shape alignment.
            \item The difference in their minor axes (used to approximate ring thickness) must fall between 2 and 50 pixels.
            \item Both ellipses must have a minimum minor axis of at least 4 pixels to ensure they are not degenerate or too flat.
            \item The aspect ratio (major/minor axis) of each ellipse must be $\leq$ 1.5, enforcing that the ellipses are roughly circular.
            \item The difference between their border thicknesses (computed from major and minor axes) must be $\leq$ 5 pixels, ensuring visual symmetry of the ring.
        \end{itemize}
        \item After satisfying these 2D constraints, each candidate undergoes a 3D depth validation step. Specifically, 10 radial depth samples are taken inside the inner ellipse (center region) and between the two ellipses (ring region). The ring is accepted only if the median depth of the center is at least 1.5 meters greater than the ring border. This confirms that the ring is a hollow structure suspended in space (i.e., a real 3D ring), not a ring drawn or printed on a flat surface.
    \end{itemize}


    \item \textbf{Color Classification:}
    \begin{itemize}
        \item A binary ring mask is created from the area between the inner and outer ellipses, slightly eroded to reduce noise, and applied to the HSV image.
        \item A 180-bin hue histogram is computed over the masked region, smoothed with a circular Gaussian ($\sigma = 3$), and normalized.
        \item The histogram is compared to predefined reference histograms for red (0°), green (60°), and blue (120°) using cosine similarity.
        \item If the average V (value) channel in the ring region is below 0.35, the ring is classified as \texttt{black}; otherwise, the color with the highest similarity score is selected.
    \end{itemize}


    \item \textbf{Ring Grouping and Publishing:}
    \begin{itemize}
        \item Ring detections are grouped if they occur within 0.5 meters of each other.
        \item Groups with at least 3 observations are used to determine the average position and majority color.
        \item Published ring detections (\texttt{DetectedRing} messages on \texttt{/ring\_position}) include timestamp, color, and 3D map coordinates.
        \item Previously published detections are tracked and not duplicated.
    \end{itemize}
\end{itemize}
The \texttt{ring\_detector.py} script is responsible for these operations.

\subsection{Face Detection and Gender Recognition}
For human-robot interaction, our system first detects human faces and then attempts to recognize their gender. This process utilizes synchronized RGB images and point cloud data.
\begin{itemize}
    \item \textbf{Face Detection:} We use a general YOLOv8n (You Only Look Once) model \cite{Redmon2016}, obtained from \href{https://github.com/ultralytics/ultralytics}{Ultralytics}, to detect human faces (class 0) in the RGB camera feed (from \texttt{/oakd/rgb/preview/image\_raw}). Detections are filtered based on a confidence threshold (typically 0.6).
    \item \textbf{Gender Recognition:} Once a face is detected and its bounding box extracted, the cropped face region is passed to a pre-trained Vision Transformer (ViT) model for gender classification. Specifically, we use the \texttt{dima806/fairface\_gender\_image\_detection} model available on Hugging Face \cite{FairFaceGenderModel}. This model classifies the face as "man" or "woman" with reported accuracy around 93.4\%. The implementation uses the \texttt{transformers} library by Hugging Face.
    \item \textbf{3D Localization and Normal Estimation:} For each valid face detection (passing depth checks, e.g., within 1.5m), its 3D position in the camera frame is determined using the synchronized point cloud data \\(from \texttt{/oakd/rgb/preview/depth/points}). A small window of points around the face's 2D center is extracted from the point cloud. RANSAC-based plane fitting is applied to these points to estimate the 3D centroid of the facial surface and its normal vector. This normal is oriented to face the camera, and an interaction point is calculated at a short offset along this normal.
\end{itemize}
The \texttt{face\_detector.py} script manages this pipeline, including grouping multiple detections of the same individual, transforming coordinates to the map frame, and publishing confirmed detections.

\subsection{Human-Robot Interaction (Speech)}
Effective communication with simulated humans is achieved through a dedicated dialogue module (\texttt{dialogue.py}) that integrates a graphical user interface (GUI), speech-to-text (STT), text-to-speech (TTS), and natural language understanding (NLU) capabilities.
\begin{itemize}
    \item \textbf{Graphical User Interface (GUI):} A \texttt{tkinter}-based chatbox (\texttt{ChatboxGUI}) provides a visual interface for the dialogue, displaying conversation history and allowing users to type responses or trigger voice input. It also handles microphone device selection, prioritizing 'pulse' audio devices for better compatibility.
    \item \textbf{Speech-to-Text (STT):} The \texttt{speech\_recognition} library, configured to use the Google Speech Recognition API, converts spoken user input (captured via microphone) into text.
    \item \textbf{Text-to-Speech (TTS):} The \texttt{pyttsx3} library is used to synthesize robot speech, providing audible responses to the user.
    \item \textbf{Natural Language Understanding (NLU):}
        \begin{itemize}
            \item Recognized user text is processed by the \texttt{SpeechResult} class.
            \item \texttt{spaCy} (using the \texttt{en\_core\_web\_sm} model, if available) is employed for basic NLP tasks.
            \item Bird species are extracted from user utterances by matching against a predefined list (\texttt{BIRD\_SPECIES}) and associated keywords (\texttt{BIRD\_KEYWORDS}).
            \item User responses are also checked for positive (e.g., "yes", "sure") and negative (e.g., "no", "nope") keywords to understand affirmations or negations.
        \end{itemize}
    \item \textbf{Dialogue Flow (\texttt{BirdDialogue} class):}
        \begin{itemize}
            \item The dialogue is gender-specific, initiated based on the gender information received (e.g., from the \texttt{face\_detector\_node}).
            \item \textbf{Dialogue with Women:} The robot asks for their favorite bird. If a bird is successfully extracted, its location is described.
            \item \textbf{Dialogue with Men:} The robot asks for their favorite bird and then enters a confirmation loop ("Are you sure?"). The user can confirm, or state a different bird. The robot proceeds once a bird choice is confirmed or a new bird is mentioned multiple times.
            \item \textbf{Location Description:} If a bird is identified, its location is described in relation to the park's regions ("West", "Center", "East" based on coordinates) and the color of the nearest ring, using pre-supplied lists of known bird and ring locations.
        \end{itemize}
\end{itemize}
This system is designed to be invoked when an interaction is required, taking the detected gender and current environmental knowledge (bird/ring locations) as input.

\subsection{ROS Node Architecture}
Our system is architected as a set of loosely coupled ROS nodes, each responsible for a specific functionality. This modular design facilitates development, testing, and debugging. Key nodes include:
\begin{itemize}
    \item \texttt{navigator} (from \texttt{navigator.py}): This is the central navigation node that controls the robot state and it's actions.
    
    \item \texttt{bird\_detector} (from \texttt{bird\_detector.py}): This node implements the two-stage bird detection and classification pipeline.
        
    \item \texttt{ring\_detector} (from \texttt{ring\_detector.py}): Processes camera images to detect rings and their colors. Publishes ring information.
    \item \texttt{face\_detector} (from \texttt{face\_detector.py}): This node handles the detection of human faces and subsequent gender classification.

    \item \texttt{bridge\_navigation} (from \texttt{bridge\_navigation.py}): This node is responsible for visually navigating the bridge.
    
\end{itemize}

\subsection{Bridge Crossing}
Navigating the bridge involves robust visual perception and dynamic pose estimation using the robot's top-mounted arm camera. The processing pipeline adapts based on the robot’s situation and environment, and proceeds through the following stages:

\begin{itemize}
    \item \textbf{Image Preprocessing:} The RGB input from \texttt{/top\_camera/rgb/preview/image\_raw} is converted to HSV. The Hue channel is blurred and thresholded using Otsu's method, then inverted to highlight the bridge structure. This binary image serves as the foundation for further analysis.

    \item \textbf{Guardrail Detection and Path Guidance:}
    \begin{itemize}
        \item \textbf{Edge and Corner Removal:} Canny edge detection is applied. Harris corners are detected and removed from the upper third of the image and, if needed, the entire image to suppress noise from bridge-land transitions.
        \item \textbf{Component Analysis and Line Fitting:} The two largest edge components are selected. Each is segmented into vertical slices, and line segments are fit using \texttt{cv2.fitLine}. Metadata including endpoints, angles, parent edge ids and centers is stored.
        \item \textbf{Line Pairing and Filtering:} Pairs of left and right lines are formed based on angular similarity ($\leq$ 60°), spatial separation (20–80\% of image width), and different component IDs. Pairs with abrupt direction changes ($>$ 35°) are filtered out.
        \item \textbf{Pose Calculation:} For the final valid pair, the midpoint is computed and a forward direction vector is inferred. This 2D image pose is transformed into a 3D pose in the \texttt{map} frame using synchronized point cloud data from \texttt{/top\_camera/rgb/preview/depth/points}.
    \end{itemize}
    \item \textbf{End-of-Bridge Detection:} When crossing from the water bridge onto land, visual segmentation temporarily fails. To handle this, the system checks if the top 20 rows of the binary image are fully white. If so, it assumes the robot is at the edge of the bridge and blindly advances. A forward pose is computed from a fixed point in the image and transformed to the map frame for navigation.

    \item \textbf{Red X Marker Detection:} After reaching land, the robot seeks a red X stop marker indicating the final goal location.
    \begin{itemize}
        \item The lower central portion of the image is masked to avoid the robot's body.
        \item The remaining binary mask is eroded and thresholded again to isolate colored regions on the path.
        \item Connected components are analyzed, and for large enough blobs, hue histograms are computed and compared to a red reference histogram using cosine similarity.
        \item If similarity exceeds 0.75, the blob is accepted as a red X, and its center point is projected into a final 3D pose for navigation.
    \end{itemize}
    
\end{itemize}

The \texttt{bridge\_navigation.py} node publishes the resulting pose as a \texttt{BridgePose} message to the \texttt{/bridge\_pose\_map} topic, tagging it as a final goal if a red X is detected. The node is active only when the robot is in the \texttt{BRIDGE\_NAVIGATION} or \texttt{GO\_TO\_FINAL\_POSITION} state, unless manually overridden.

\subsection{Communication and Data Flow}

The core logic of the robot is implemented in the main navigation node (\texttt{navigator.py}), which is responsible for coordinating all high-level behavior throughout the task. This script maintains the robot's current operational state via a finite state machine, guiding the robot through stages such as exploring the park, approaching birds, interacting with humans, and crossing the bridge. That state is being broadcast to every node with the topic \texttt{/robot\_internal\_state}.

The navigation node subscribes to several topics to receive information from perception and planning nodes. This data is used to update internal structures such as the list of known birds, rings, and people to interact with.

\begin{itemize}
    \item \texttt{/detected\_faces} (from \textbf{face\_detector}): 
    New face groups are added to an internal queue for future interactions.
    
    \item \texttt{/ring\_position} (from \textbf{ring\_detector}): 
    Detected ring groups are stored in a list used to guide bird localization.

    \item \texttt{/detected\_birds} (from \textbf{bird\_detector}): 
    Detected and classified birds are added to an internal list to avoid duplicate visits.

    \item \texttt{/bird\_initial\_position\_detection} (from \textbf{bird\_detector}): 
    Triggered when a bird is spotted at a goal; the navigator checks costmaps and sends a navigation goal.

    \item \texttt{/inspection\_markers} (from \textbf{planner}): 
    During initialization, a list of exploration waypoints is received and stored in a goal queue.
\end{itemize}

\section{Results}

\subsection{Evaluation Run}

During the evaluation run, the system performed reliably across most tasks. It successfully detected all human faces and all colored rings, and accurately localized birds relative to their associated rings. The dialogue system correctly simulated conversations and responded according to the person’s gender and preferences. Bridge traversal was also completed without issues, and the robot successfully followed the designated path to the final parking position marked by the red X.

One notable failure occurred during bird classification: a small bird (kingfisher) was not correctly classified due to insufficient frame generation. This issue was primarily caused by the high computational load and synchronizing RGB images, depth images, and point clouds, which lowered the detection rate and reduced the number of classification attempts. Additionally, the entire evaluation run took significantly longer than earlier test runs, as it was executed on a less powerful computer than the one used during development, amplifying the performance bottlenecks introduced by resource-intensive modules.



\subsection{Module Performance}

\begin{itemize}
    \item \texttt{navigator} (from \texttt{navigator.py}):  
    Functioned reliably, using A* for path planning. However, it is not optimal for multi-goal planning (e.g., visiting all birds), where solving a Traveling Salesman Problem (TSP) would be better, though too computationally intensive for our system.

    \item \texttt{bird\_detector} (from \texttt{bird\_detector.py}):  
    Generally accurate, but occasionally failed to classify smaller birds due to limited resolution. The module is resource-heavy due to simultaneous use of YOLO and ResNet, and the need for high-resolution camera input.

    \item \texttt{ring\_detector} (from \texttt{ring\_detector.py}):  
    Performed reliably in detecting and validating ring geometry and color. However, the use of high-resolution images combined with geometric and depth-based validation made it computationally demanding.

    \item \texttt{face\_detector} (from \texttt{face\_detector.py}):  
    Detected faces accurately and performed well overall. Gender classification relied on a transformer-based model, which was computationally expensive.

    \item \texttt{bridge\_navigation} (from \texttt{bridge\_navigation.py}):  
    Functioned correctly under most conditions. However, noisy AMCL localization estimates sometimes resulted in misaligned navigation goals.

    \item \texttt{dialogue} (from \texttt{dialogue.py}):  
    Limited interaction due to poor microphone quality. The system relied on simple keyword-based recognition, which occasionally failed to detect bird names correctly due to lack of context awareness.
\end{itemize}

\section{Conclusion}
Team Pi successfully developed an integrated robotic system capable of addressing the multifaceted challenges of Task T2s within the bird park simulation. Our robot demonstrated capabilities in autonomous navigation, bird, ring and face detection and recognition, human-robot interaction via speech and gender detection, and specialized maneuvers like bridge crossing.

Throughout this project, we encountered several technical challenges:
\begin{itemize}
    \item \textbf{Simulation Environment Quirks:} We faced issues with the Gazebo simulation environment. Initially, the Ogre rendering engine did not render the sky, requiring a switch to Ogre2. We also had to debug a problem where point cloud coordinates were unexpectedly flipped by 90 degrees in a configuration file, which complicated initial setup and localization efforts.

    \item \textbf{Resource Limitations:} Development was constrained by the need to use lab computers, as running the full simulation and ROS environment on personal laptops was often not feasible. This limited our access and sometimes slowed down the development and testing cycles.

    \item \textbf{Integration Complexity:} Integrating multiple perception, navigation, and interaction modules into a reliably functioning system is inherently complex. Ensuring robust data flow, timing, and error handling across different ROS nodes required significant effort.

    \item \textbf{Synchronization Issues:} Several perception modules, especially those that estimate 3D positions using point cloud data, required strict synchronization of RGB images, depth images, and point clouds. Without synchronized messages, even minor delays could result in mismatched frames, leading to large spatial errors when estimating object positions. We used ROS 2 message filters to address this issue and ensure time-aligned data across sensors.
\end{itemize}


Despite these challenges, the project was a valuable learning experience, providing deep insights into the practical aspects of developing intelligent robotic systems. We were able to apply theoretical knowledge to solve concrete problems and work collaboratively to build a complex system.
Future work could focus on enhancing the robustness of individual modules, particularly improving the accuracy of classification tasks under varying conditions.
